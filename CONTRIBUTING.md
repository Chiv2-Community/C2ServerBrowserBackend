# Contributing

## API development

The API is OpenAPI-first. Define every endpoint, request, response, and external
token model in `assets/chiv2-server-browser-api.yaml` before implementing it.
This includes the TBIO/PlayFab compatibility endpoints and non-JSON responses.

The uv workspace contains five runtime packages and one development-tooling project:

- Root: `chivalry2-unofficial-server-browser-backend`, handwritten application
  handlers and domain state in `src/server_browser_backend`.
- `packages/server-browser-models`: generated models, model runtime, and contract.
- `packages/server-browser-client`: generated sync/async HTTPX clients.
- `packages/server-browser-server`: framework-neutral abstract handler interfaces.
- `packages/server-browser-fastapi`: generated FastAPI adapter.
- `packages/server-browser-codegen`: generation CLI, toolchain, configuration,
  module-scoped templates, and generation tests (development-only).

See [Python packages](docs/python-packaging.md) for dependency boundaries, client
usage, alternative implementations, and migration from `server-browser-api`.

Generated SDK sources under the four reusable runtime projects are never edited by
hand. Application handlers implement the generated interfaces and return typed
`ApiResponse` values. Domain conversion functions belong in the application,
not in generated models. Do not declare routes in the application.

Install uv, Python 3.10 or newer, and Java 11 or newer (CI uses Java 21), then:

```bash
uv sync --frozen --all-packages
uv run server-browser-codegen
./ci.sh
```

On Windows, run `./ci.ps1` instead of `./ci.sh`. OpenAPI Generator is pinned in
the codegen project; its CLI invokes that installed version rather
than a global generator. Normal application startup needs neither Java nor the
generator. Generated Python sources are committed. Bundled `openapi.yaml` and
`contract.json` copies are gitignored and generated by the package build hook,
including editable installs; packaging needs PyYAML but not Java. Sdists include
the authoritative YAML so wheels can also be built outside this repository.

For API changes:

1. Edit OAS. Give each operation a unique `operationId` and one API tag. Declare
   request defaults, nullable fields, wire names, status codes, and response types.
2. Run generation. Never patch the output to resolve a generator issue.
3. Implement the generated abstract methods and application conversions.
4. Add compatibility and contract tests; commit the OAS and generated diff.

`packages/server-browser-codegen/src/server_browser_codegen/config.yaml` selects
`python-fastapi`. Its sibling `templates/` directory groups templates by output
owner: `models/`, `client/`, `server/`, and `fastapi/`, with common markers in
`shared/`. Change these only for generator behavior, never for operation-specific
business logic.
OAS remains the source of route names, signatures, and model fields. Request
constraints are validated against the packaged OAS, without runtime network
schema retrieval.

`base_api.mustache` generates ABCs with `@abstractmethod`; `api.mustache`
generates `create_router(implementation)`. Application startup passes concrete
implementations explicitly. There is no subclass scanning, implicit construction,
or generated implementation file to fill in. Synchronous handlers run in the
ASGI thread pool so existing file I/O and EOS HTTP requests do not block the loop.
Handlers receive a framework-neutral `RequestContext` with the client IP, not
FastAPI requests or Flask request globals. Only the adapter handles HTTP objects.

`main.py` is the composition root. It reads configuration, constructs the registry,
IP lists, request policy, and token reissuer once, then injects them into
`BrowserApi` and `CompatibilityApi` through required constructor arguments.
`application.Application` binds those instances to the generated routers and
captures error-display configuration per application. The handlers do not look
up services through globals, `app.state`, or request-time dependency resolution.
The diagnostic-IP setting is an injected callable so its existing environment
lookup behavior is preserved. MOTD storage is an injected directory.

Library and route imports do not construct the production application. Uvicorn
still loads `server_browser_backend.main:app`; importing that entry point creates
the production graph. Tests construct isolated graphs with their own IP-list
files and can inject alternate token services, registries, configuration, and
MOTD directories. Registry state and signing keys remain process-local.

The compact model override preserves OAS defaults (including empty lists), wire
aliases, omitted versus nullable fields, and union serialization. The transport
decodes requests against the packaged OAS before Pydantic construction, preserving
the existing JSON 400 errors instead of adopting FastAPI's default 422 responses.
Responses use the declared wire models without filtering diagnostic IP subtypes.
`app.openapi()` returns the packaged contract; framework-generated docs routes
are disabled. Production runs directly under Uvicorn, without Gunicorn.

OAS `string` formats `ip-address` and `legacy-ip-address` map to typed Pydantic
aliases of `IPv4Address | IPv6Address` through the codegen project's config. Both accept
raw literals and single-bracketed IPv6 input; neither accepts hostnames, CIDRs,
ports, or bracketed IPv4. Registration, diagnostic, PlayFab, and TBIO address
fields remain parsed objects until JSON serialization. The ordinary format emits
raw canonical literals; the legacy format emits IPv6 in square brackets exactly
once and leaves IPv4 unbracketed. CIDR ban/verified-list entries remain network
strings, not host-address models.
Invalid `/check-banned/{ip}` parameters now return JSON 400 rather than reaching
the network parser as unchecked strings. The wheel smoke test also opens a real
IPv6 loopback listener when available and checks bracketed registration, TBIO
brackets, and raw PlayFab output over that socket.

`uv run server-browser-codegen --check` regenerates into a temporary
directory and rejects missing, extra, stale, or hand-edited generated Python files.
The ignored contract copies are excluded from drift checks; contract tests and
wheel checks compare them with the authoritative YAML. Generation also refreshes
the local copies after OAS edits.
CI also checks exact runtime/OAS route parity, response schemas, handler
implementations, client round trips, type checking, all package builds, and
isolated wheel startup. `uv build --all-packages` builds all six distributions,
including the development-only codegen tool.
Run `uv run mypy` for type checking; `pyproject.toml` defines the shared source
paths, including every workspace project's `src/` directory.
`uv run python scripts/check_wheels.py` rebuilds every sdist outside the checkout,
checks framework-free models/client/interfaces installs and the installed codegen
CLI from outside the checkout, then starts the backend
from the rebuilt wheels. Keep one current wheel and sdist per package in `dist/`.
Consumers install only their chosen package and its dependency wheels. For
example, install the models and client wheels together with `pip install`;
alternatively use `pip install --find-links ./dist server-browser-client`.

Compatibility endpoints retain their URLs and wire casing. Malformed JSON
objects now receive JSON validation errors rather than incidental internal
errors. Registration retains missing `mods`/`password_protected` defaults;
ordinary server responses still omit diagnostic IP fields.

Run `uv run python scripts/check_compatibility.py` to replay deterministic HTTP
sequences against pre-migration commit `80e1fae`. It exports the baseline into a
temporary directory, installs it separately, and fixes clocks, UUIDs, secrets,
and signing keys. It compares status, parsed JSON, content type, Allow headers,
registry state, and configuration-file contents. The baseline commit must exist
locally; dependency installation needs package access. This is an additional
manual check, not part of the shallow-checkout CI job.

Three narrowly allowed differences are reported, not hidden:

- Missing admin headers on ban/verified list reads: accidental 500 becomes 403.
- Explicit null local IP: still 400, but the expected type is `str`, not the
  removed internal `IPAddress` wrapper.

`--strict` rejects these too. The replay is bounded evidence, not exhaustive
equivalence: malformed compatibility requests intentionally return JSON 400s,
framework-level 404/405 error bodies differ, and live plugin/launcher integration
has not been exercised. Swagger content intentionally changes with the contract.

## Publishing

Docker uses a wheel-builder stage and a clean runtime stage. The builder exports
locked non-development dependencies, builds the backend plus models/interfaces/
FastAPI wheels, and installs them into a virtual environment. The final image
copies only that installed environment, default configuration, and the startup
script. It contains no repository checkout, client/codegen sources, workspace
manifests, or uv executable; startup invokes the installed Uvicorn directly.

CI and tag workflows retain all six wheels and sdists plus the authoritative
OpenAPI YAML in the `python-distributions-and-contract` Actions artifact. This
makes the contract available to non-Python tooling without another package.
Publishing a GitHub Release triggers `.github/workflows/release-packages.yml`,
which checks out its tag, validates all packages, and attaches the wheels,
sdists, and authoritative YAML to that release. It does not create releases or
overwrite existing assets. No package-index publication is configured; verify
name ownership before adding it. The four generated distributions use one coordinated version and
exact internal dependency constraints; update their `pyproject.toml` versions and
the backend requirements together, then refresh `uv.lock` and run `./ci.sh`.
The development-only codegen tool has its own version and owns the pinned
generator dependency; it is never installed in runtime SDK/backend environments.
See its [README](packages/server-browser-codegen/README.md) for template ownership
and the installed `--root` command.

The GitHub Actions workflow in `.github/workflows/publish.yml` tests and publishes
the tagged commit to `ghcr.io/chiv2-community/c2serverbrowserbackend` when a
`vMAJOR.MINOR.PATCH` tag, optionally followed by `+build.metadata`, is pushed.
Plain release tags publish the version without `v` and update `latest`.
Tags with build metadata do not update the `:latest` tag.
The version comes from the Git tag, not `pyproject.toml`.

The workflow caches uv dependencies and stores Docker build layers in the GHCR
`buildcache` tag for reuse across releases. This tag is build cache, not a runnable
release image.

The workflow authenticates with the built-in `GITHUB_TOKEN` using
`packages: write`; no registry secrets are required. Organization policies must
allow the workflow to create packages. After the first publish, set the package
visibility to public in its GitHub package settings to allow anonymous pulls.

After the workflow is merged into `main`, tag the desired release commit:

```bash
git switch main
git pull --ff-only origin main
git tag v1.1.0
git push origin refs/tags/v1.1.0
```

Use a new version for each release. Prerelease tags are not supported.
Do not run `publish.sh` or `publish.ps1` for tag-triggered releases; those scripts
publish to Docker Hub and create tags themselves.
